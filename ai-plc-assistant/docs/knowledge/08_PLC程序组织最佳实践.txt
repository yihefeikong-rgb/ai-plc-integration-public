西门子 S7 PLC 程序组织最佳实践

========================================
第一部分：OB 组织块分类
========================================

OB1 — 主循环 OB
  CPU 的主扫描周期，每个周期执行一次。
  仅包含 FB/FC 调用，作为程序"目录"，不包含直接逻辑。

OB100 — 启动 OB
  CPU 启动时执行一次。
  用于初始化变量、设置默认值、建立通信连接。

OB30-OB38 — 循环中断 OB
  固定时间间隔执行（如 100ms、200ms）。
  用于 PID 控制、时间关键任务。
  必须保证执行时间小于中断周期。

OB82 — 诊断 OB
  I/O 模块诊断事件触发。
  用于处理模块故障检测。

OB80-OB87 — 错误处理 OB
  运行时错误触发。
  防止 PLC 进入 STOP。

OB10-OB17 — 时间中断 OB
  定时触发（如每天 8:00 执行）。
  用于数据日志归档、报表生成。

关键原则：OB1 保持为"目录"，仅顺序调用命名的 FB/FC，不包含直接逻辑。

========================================
第二部分：FB 与 FC 的使用
========================================

功能块 FB（带实例 DB，有记忆）：
  使用场景：
  - 电机控制（需要运行状态保持）
  - 阀门控制（需要开/关状态）
  - PID 环路（需要积分值保持）
  - 报警处理器（需要报警状态锁存）
  - 状态机（需要当前步数保持）

  特点：
  - 有实例 DB，在扫描周期间保持 In/Out/Static 值
  - 支持多实例（Multi-instance FB）
  - 有记忆，需要保持状态用 FB

函数 FC（无实例 DB，无记忆）：
  使用场景：
  - 数学运算（加法、缩放）
  - 数据转换（温度转换、单位转换）
  - 简单工具函数（逻辑分组）
  - 纯计算（不需要内部记忆）

  特点：
  - 无实例 DB，每次调用重新初始化所有参数
  - 每次调用单独使用

经验法则：
  需要在调用之间保持状态（记忆）？用 FB。
  纯计算或工具函数？用 FC。

========================================
第三部分：数据块组织
========================================

Global DB vs Instance DB：
  Instance DB — 与 FB 关联，存储 FB 的 In/Out/Static 数据
  Global DB — 独立于块，存储全局数据

Global DB 按用途分类：
  工厂设置 DB — 校准参数、永久配置
  操作员输入 DB（保持型）— 需跨断电保持的设定值
  操作员输入 DB（非保持型）— 临时操作员调整
  HMI 显示 DB — 映射给操作员可视化的标签
  内部程序 DB — 中间计算、状态机
  跨 PLC 数据 DB — 通信共享标签

重要规则：
  - 禁止使用位存储器（M）存储持久数据，改用全局 DB
  - 优化数据块是 S7-1200/1500 的默认选择
  - 需要 PUT/GET 通信的 DB 必须关闭优化访问

========================================
第四部分：命名约定
========================================

推荐命名规范：

块对象：UpperCamelCase — MotorControl, ValveHandler
常量：UPPER_CASE — MAX_SPEED, TIMEOUT_DELAY_MS
输入变量：in 前缀 — inSensorValue
输出变量：out 前缀 — outMotorCmd
InOut 变量：io 前缀 — ioRunState
临时变量：temp 或 _ 前缀 — tempResult

数据类型前缀：
  b — BOOL，示例：bMotorRun, bAlarmActive
  i — INT，示例：iCounter, iTemperature
  r — REAL，示例：rSpeed, rPressure
  s — STRING，示例：sAlarmText
  dt — DATE_TIME，示例：dtStartTime
  t — TIME，示例：tDelayStart

I/O 标签命名：
  格式：[区域]_[设备]_[功能]_[状态]
  示例：Mixer_01_Motor_RunFeedback, Conveyor_Infeed_Prox_Sensor

========================================
第五部分：层次化程序结构
========================================

五层架构模型：

  Level 5: 应用/主序列（状态机：AUTO/MANUAL/ERROR）
  Level 4: 过程协调（顺序器、模式管理器）
  Level 3: 设备协调（运动、阀组、安全）
  Level 2: 设备驱动（伺服接口、单阀、AI模块）
  Level 1: 硬件抽象（I/O 映射、现场设备驱动）

典型调用树：
  OB1 (Main)
    └── FC_SystemControl（操作模式）
         ├── FB_PackMLStateMachine（顺序控制）
         │    ├── FB_MotorControl（设备层）
         │    ├── FB_ValveControl（设备层）
         │    └── FB_ConveyorControl（设备层）
         └── FC_AlarmHandler（工具层）

各层职责：
  执行层（OB1/循环OB）— 顺序调用 FB/FC
  控制逻辑（FC）— 过程逻辑、分组
  设备控制（FB 多实例）— 电机、阀门、执行器
  库块（FB 标准）— PID、缩放、通信
  数据存储（DB）— 按用途组织

========================================
第六部分：编程语言选择
========================================

SCL/ST — 复杂算法、计算、状态机
  建议占比 80%，可读性高，可维护性好

LAD — 简单联锁、急停逻辑
  电工友好，适合维护人员查看

FBD — 控制环路、数据流
  适合 PID 等连续控制逻辑

SFC — 顺序控制（GRAFCET）
  适合复杂状态机、工步控制

========================================
第七部分：UDT 与库管理
========================================

  - 为重复设备（电机、阀门、传感器）创建 UDT
  - 可重用元素作为类型放入库中
  - 库必须带版本号管理
  - 使用优化块获得更好性能
  - 禁止使用位存储器(M)，改用全局 DB

FB 封装原则：
  - 每个 FB 通过接口（In/Out）与外部逻辑通信
  - 禁止在块中混合接口传参和直接全局数据访问
  - 优先使用 UDT 代替 STRUCT
  - 优先使用 CASE 指令而非 IF..ELSE..ELSEIF

========================================
第八部分：IEC 61131-3 结构原则
========================================

POU 类型：
  PROGRAM — 顶层，循环调用，不放详细逻辑
  FB — 有内部记忆，可实例化，代表过程对象
  FC — 无内部记忆，确定性计算

变量作用域：
  VAR — 局部变量
  VAR_INPUT — 输入参数
  VAR_OUTPUT — 输出参数
  VAR_IN_OUT — 输入输出参数
  VAR_TEMP — 临时变量
  VAR_GLOBAL — 全局变量

7 步结构化方法（PLCopen）：
  1. 识别过程和控制问题
  2. 单元组合使接口和交互最少
  3. 定义所有操作员交互和监控数据
  4. 从顶层分解到逻辑分区
  5. 定义所需功能块
  6. 定义扫描周期时间要求
  7. 配置系统：定义资源、链接 I/O、分配任务

数据封装原则：
  - 应用数据被分区
  - 每个分区仅通过适当的函数集访问
  - 对不期望的使用隐藏内部数据
